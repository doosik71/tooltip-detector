## 요약

`yolov8stooltip`은 YOLOv8s 백본·넥에 Pose 헤드를 붙여, 탐지 하나가 도구 박스와 **그 도구의** 팁 좌표를 같은 앵커에서 함께 내도록 만든 모델이다. 목적은 박스와 팁을 따로 탐지한 뒤 후처리 규칙으로 짝지을 때 생기는 뒤바뀜(가까운 다른 도구의 팁을 고르는 오류)을 구조적으로 없애는 것이다. `cholec80`과 `erop`에서 각각 150에포크를 무작위 초기화로 학습하고 test 스플릿 전체로 평가했다.

결과는 다섯 가지로 정리된다.

1. **팁이 자기 도구에 붙어 나온다.** 팁 위치만 보는 Hit@10 px과 자기 도구의 팁만 맞은 것으로 세는 own tip @10 px의 차이가 `cholec80` 1.71 %p, `erop` 1.18 %p다. 이 차이는 "위치가 맞은 팁이 자기 박스에 붙지 않은 경우"의 상한이므로(§6.2), 뒤바뀜은 GT 도구의 2 % 미만이다.
2. **쌍 지표를 깎는 것은 뒤바뀜이 아니라 박스 매칭과 팁 정밀도다.** GT 도구의 19.3 % (`cholec80`) / 11.8 % (`erop`)가 IoU 0.5로 매칭되는 박스를 얻지 못했다. 매칭된 도구 안에서는 팁이 10 px 안에 들어오는 비율이 75.0 % / 85.3 %다.
3. **팁 오차 분포는 정밀한 다수와 긴 꼬리로 갈린다.** 중앙값 오차는 5.54 px / 3.00 px이고 GT 팁의 45.7 % / 64.8 %가 5 px 안에 있다. 반면 평균은 37.41 px / 24.65 px이고 P90은 131.92 px / 62.19 px다. 200 px 이상 오차의 약 75 %는 다른 GT 팁과 같은 예측에 매칭된 경우로, 도구 하나를 통째로 놓친 프레임에서 생긴다.
4. **`cholec80` 학습은 수렴하지 않았고, 키포인트 분기가 늦게 학습됐다.** 박스·클래스는 10에포크 안에 자리를 잡았지만 val pose 손실은 35에포크까지 9 안팎에 머물렀다. 최고 val mAP@0.5:0.95는 마지막 에포크(150)에서 나왔고 그때도 오르고 있었다.
5. **추론은 프레임당 5.2 ms (약 192 FPS)다.** letterbox, forward, 디코딩, NMS를 포함한 GPU 측정값이다.

## 1. 목적과 검증 질문

박스와 팁을 서로 무관한 두 클래스로 탐지하는 모델은, 어느 팁이 어느 도구의 것인지 출력에 없다. 그래서 쓰는 쪽이 후처리로 짝을 지어야 하고, 도구 박스가 가까이 겹친 프레임에서 다른 도구의 팁을 고르는 오류가 수작업 레이블링 중에 자주 발견됐다([README](../README.md)). 이 모델은 탐지 헤드를 YOLOv8-pose 구조로 바꿔, 학습 단계에서 TaskAlignedAssigner가 고른 양성 앵커가 바로 그 도구의 팁을 회귀하게 한다.

이 보고서가 답하려는 질문은 세 가지다.

- **Q1.** 출력된 팁이 실제로 자기 도구의 팁인가? (뒤바뀜이 얼마나 남는가)
- **Q2.** 쌍 단위 성능을 제한하는 요인은 무엇인가?
- **Q3.** 팁 위치 정확도와 실패 양상은 어떤가?

다른 모델과의 수치 비교는 이 보고서의 범위가 아니다.

## 2. 실험 설정

### 2.1 모델

| 항목     | 값                                                                         |
| -------- | -------------------------------------------------------------------------- |
| 구조     | YOLOv8s 백본(0〜9) + 넥(10〜21) + Pose 헤드(22)                            |
| 출력     | 탐지당 `[x1, y1, x2, y2, score, class, kx, ky]`, 클래스는 `tool` 하나      |
| 파라미터 | 11,422,265                                                                 |
| 입력     | 736 × 480 프레임을 640 × 640으로 letterbox                                 |
| 손실     | 7.5·L_box + 0.5·L_cls + 1.5·L_dfl + 12.0·L_pose, L_pose는 OKS형 (σ = 0.05) |

### 2.2 학습

두 데이터셋 모두 같은 설정이다(요약 §2): 150에포크, 배치 16, SGD lr 0.01 (momentum 0.937, weight decay 0.0005), 3에포크 warmup 뒤 cosine 감쇠, EMA 사용, `--frame-stride 5`, 에포크마다 val 1,500프레임 평가. 사전학습 가중치 없이 시작했다. 체크포인트는 val mAP@0.5:0.95(`tool` 박스와 32 px `tip` 상자의 평균)가 가장 높은 에포크로 골랐다. 학습 시간은 `cholec80` 3.7시간, `erop` 5.5시간이다(요약 §3).

### 2.3 평가

test 스플릿의 모든 프레임을 평가했다(`cholec80` 98,234 / `erop` 36,142 프레임, 요약 §4). 운용 지점은 `conf = 0.25`, NMS IoU 0.45이고, AP 곡선만 `conf = 0.001`까지 쓴다. 거리는 모두 원본 프레임(736 × 480) 픽셀이다.

데이터에 관해 두 가지를 짚어 둔다.

- **두 데이터셋의 분할 단위가 다르다.** 루트 보고서 §2.2에 따르면 `cholec80`은 영상 단위 분할(test = `video41〜80`)이고 `erop`은 프레임 단위 분할이다. `erop` test 프레임에는 학습 프레임과 시간적으로 인접한 프레임이 섞여 있으므로, 두 데이터셋의 수치 차이를 데이터셋 난이도 차이로만 읽을 수 없다.
- **도구 4개 이상 프레임이 평가에 포함돼 있다.** 루트 보고서(§2.7)는 이 프레임의 라벨 대부분이 반자동 파이프라인의 오검출이라 평가에서 제외했지만, 이 서브 프로젝트의 `eval-model`은 제외하지 않는다. 해당 프레임은 `cholec80` 2,257 / `erop` 670개, GT 팁 9,447 / 2,778개(전체의 6.1 % / 5.7 %)다(요약 §8). §7.2에서 이 구간을 따로 본다.

### 2.4 지표

| 지표            | 무엇을 세는가                                                                                                                                |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `tool` AP       | 도구 박스 탐지                                                                                                                               |
| `tip` AP        | 예측 팁 둘레 32 px 상자를 그 도구의 점수로 채점                                                                                              |
| Hit@N px        | GT 팁마다 가장 가까운 예측 팁이 N px 안에 있는 비율. 팁이 어느 도구에 붙었는지는 보지 않는다                                                 |
| own tip @N px   | GT 도구와 예측 도구를 박스 IoU ≥ 0.5로 1:1 매칭한 뒤, 예측 도구의 팁이 **그 GT 도구 자신의** 팁에서 N px 안에 있는 비율. 분모는 전체 GT 도구 |
| Hungarian @N px | GT 팁과 예측 팁을 거리 상한 N px 안에서 1:1 배정한 precision·recall                                                                          |

Hit와 own tip은 같은 예측 집합(`conf ≥ 0.25`)에서 GT 도구마다 계산된다(`scripts/eval-model.py`). 이 점이 §6.2의 상한 해석의 근거다.

## 3. 학습 경과

### 3.1 `erop`: 빠르게 자리 잡고 천천히 오른다

val pose 손실은 1에포크 11.60에서 10에포크 2.85로 떨어졌고, val own tip @10은 같은 기간에 0 %에서 74.15 %가 됐다(요약 §3). 이후 140에포크 동안 own tip @10은 85.12 %까지 11 %p 더 올랐고, mAP@0.5:0.95는 0.4713에서 0.6337로 올랐다. 최고 에포크는 147이고 마지막 5에포크의 mAP@0.5:0.95는 0.6329〜0.6337로 평탄하다. 이 데이터셋에서는 150에포크가 충분했다.

### 3.2 `cholec80`: 키포인트 분기가 늦게 학습되고 수렴하지 않았다

`cholec80`은 박스와 팁의 학습 시점이 크게 갈렸다.

| 에포크 | tool AP50 | val pose | train pose | tip AP50 | own tip @10 (%) |
| -----: | --------: | -------: | ---------: | -------: | --------------: |
|     10 |    0.7764 |     9.64 |       6.59 |   0.0490 |           19.53 |
|     25 |    0.7962 |     9.06 |       5.96 |   0.0849 |           28.37 |
|     26 |           |     9.06 |       4.37 |          |                 |
|     35 |           |     9.01 |       4.02 |   0.0995 |           32.91 |
|     51 |           |     5.95 |       3.84 |   0.2296 |           49.68 |
|     61 |           |     5.10 |       3.75 |   0.4127 |           63.36 |
|    100 |    0.8354 |     4.71 |            |   0.4497 |           65.70 |
|    150 |    0.8415 |     4.03 |            |   0.5090 |           70.55 |

`tool` AP50은 10에포크에 이미 최종값의 92 %(0.7764 / 0.8415)였다. 반면 val pose 손실은 35에포크까지 9.0〜9.6에 머물다가, 35〜61에포크 사이에 9.01에서 5.10으로 떨어졌다. own tip @10과 `tip` AP50도 이 구간에서 함께 뛰었다. train pose 손실은 25→26에포크 한 번에 5.96에서 4.37로 꺾였지만 val pose는 그 뒤 10에포크 동안 움직이지 않았다. 학습률은 그 사이 0.0095 부근에서 매끄럽게 감소하고 있었고 에포크 시간(88〜89초)도 일정해, 이어 학습하거나 스케줄이 바뀐 흔적은 없다.

로그된 pose 손실은 12.0 × 평균(1 − exp(−e))이므로 최댓값이 12다. val pose 9.06은 양성 앵커 평균 1 − exp(−e) ≈ 0.76, 즉 대부분의 키포인트 오차가 σ로 정한 허용 범위를 크게 벗어나 있던 상태다. 1 − exp(−e)의 기울기는 exp(−e)에 비례하므로 이 영역에서는 키포인트 회귀 신호가 약하다. **σ = 0.05의 OKS형 손실이 학습 초기에 포화해 키포인트 학습을 늦췄다는 것은 가설이다.** `erop`에서는 같은 σ로 바로 학습됐으므로 데이터셋의 도구 크기·팁 위치 분포와 함께 작용했을 것이고, 이 산출물만으로는 원인을 가릴 수 없다. σ를 바꾸거나 학습 초기에만 σ를 키운 실행으로 검증할 수 있다.

수렴 여부도 다르다. 최고 val mAP@0.5:0.95(0.4565)는 마지막 에포크에서 나왔고 마지막 5에포크 값이 0.4540에서 0.4565로 계속 올랐다. 키포인트 분기가 약 35에포크를 잃고 시작한 만큼, `cholec80`에는 150에포크가 부족했을 가능성이 크다.

### 3.3 val 지표와 test 지표는 직접 비교할 수 없다

학습 중 val own tip @10은 `cholec80` 70.55 % / `erop` 85.12 %이고, test에서는 60.52 % / 75.19 %다. 이 차이를 일반화 격차로 읽으면 안 된다. 학습 중 검증(`train-model.py`의 `validate`)은 `conf = 0.001`, NMS IoU 0.6의 예측으로 쌍 지표를 계산하고 거리를 letterbox 입력(640 px) 좌표에서 잰다. test 평가는 `conf = 0.25`, 원본 좌표다. 낮은 임계값은 박스 매칭 후보를 늘리고, letterbox 좌표의 10 px은 원본 약 11.5 px이다. val 지표는 체크포인트 선택과 곡선 모양을 보는 용도로만 쓴다.

## 4. 탐지 성능

| 데이터셋   | tool AP@0.5 | tool AP@0.5:0.95 | tip AP@0.5 | tip AP@0.5:0.95 |
| ---------- | ----------: | ---------------: | ---------: | --------------: |
| `cholec80` |      0.8622 |           0.7054 |     0.5159 |          0.2412 |
| `erop`     |      0.9227 |           0.8175 |     0.7137 |          0.4093 |

(요약 §4)

`tip` AP가 `tool` AP보다 크게 낮은 것은 상당 부분 지표의 기하 때문이다. 한 변 32 px인 두 정사각형의 IoU가 0.5 이상이려면 중심 거리가 축 방향으로 10.7 px, 대각 방향으로 8.3 px 안이어야 한다. IoU 0.95는 축 방향 0.82 px 안을 요구한다. 즉 `tip` AP@0.5는 대략 "8〜11 px 안" 기준이고, AP@0.5:0.95는 1 px 미만의 정밀도까지 평균에 넣는다. 중앙값 오차가 3〜5.5 px(§5)인 모델에서 `tip` AP@0.5:0.95가 0.24 / 0.41에 그치는 것은 이 정의에서 예상되는 값이다. 팁 성능은 `tip` AP보다 §5의 픽셀 거리 지표로 읽는 것이 맞다.

## 5. 팁 위치 정확도 (Q3)

### 5.1 전체 지표

| 데이터셋   | 탐지 실패율 | Hit@10 px | Hit@20 px | Hit@50 px |  중앙값 |     평균 |       P90 |
| ---------- | ----------: | --------: | --------: | --------: | ------: | -------: | --------: |
| `cholec80` |      2.57 % |   62.23 % |   71.93 % |   80.60 % | 5.54 px | 37.41 px | 131.92 px |
| `erop`     |      2.36 % |   76.37 % |   81.87 % |   86.73 % | 3.00 px | 24.65 px |  62.19 px |

(요약 §5) 탐지 실패율은 `conf ≥ 0.25` 탐지가 하나도 없는 프레임의 GT 팁 비율이다.

### 5.2 정밀한 다수와 긴 꼬리

| 오차 구간  | `cholec80` (전체 GT 대비) | `erop` (전체 GT 대비) |
| ---------- | ------------------------: | --------------------: |
| 0〜5 px    |                    45.7 % |                64.8 % |
| 5〜10 px   |                    16.5 % |                11.6 % |
| 10〜50 px  |                    18.4 % |                10.4 % |
| 50〜200 px |                    10.8 % |                 7.1 % |
| ≥ 200 px   |                     6.0 % |                 3.8 % |

(요약 §7의 구간을 합친 값)

분포는 두 덩어리다. 팁을 제대로 짚은 경우는 대부분 5 px 안에 있고, 나머지는 수십〜수백 px 떨어져 있다. 평균(37.41 / 24.65 px)이 중앙값의 7〜8배인 것은 이 꼬리 때문이다.

200 px 이상 오차로 매칭된 팁의 75.6 % (`cholec80`) / 75.1 % (`erop`)는 같은 프레임의 다른 GT 팁과 같은 예측에 매칭됐다(요약 §7). Hit 지표는 GT 팁마다 가장 가까운 예측을 고르므로, 도구 두 개 중 하나만 탐지되면 놓친 도구의 GT 팁이 남은 도구의 팁에 매칭돼 큰 거리를 낸다. 즉 이 꼬리의 대부분은 **위치를 틀린 것이 아니라 도구 하나를 통째로 놓친 것**이다.

### 5.3 운용 지점: Hungarian 1:1

| 데이터셋   | cap   | precision | recall | 매칭 팁 중앙값 |
| ---------- | ----- | --------: | -----: | -------------: |
| `cholec80` | 10 px |    0.6703 | 0.6220 |        3.15 px |
| `cholec80` | 50 px |    0.8516 | 0.7903 |        4.09 px |
| `erop`     | 10 px |    0.7960 | 0.7636 |        2.28 px |
| `erop`     | 50 px |    0.8962 | 0.8597 |        2.57 px |

(요약 §5) 1:1 배정에서도 매칭된 팁의 중앙값 오차는 2〜4 px다. 거리 상한을 10 px에서 50 px로 넓혀도 recall이 16.8 %p / 9.6 %p만 오르는 것은, 놓친 팁이 근처에 예측이 없는 경우(도구 미탐지)가 많다는 뜻이다. 50 px 상한에서도 FP가 21,316 / 4,856개 남는데, 이것은 GT 도구가 없는 위치의 탐지이거나 한 도구에 대한 중복 탐지다. 둘을 나누는 값은 산출물에 없다.

## 6. 도구-팁 쌍 (Q1, Q2)

### 6.1 own tip을 박스 매칭과 팁 정밀도로 나눈다

| 데이터셋   | 박스 매칭 | own tip @10 | own tip @20 | own tip @50 | 매칭 쌍 팁 중앙값 |
| ---------- | --------: | ----------: | ----------: | ----------: | ----------------: |
| `cholec80` |   80.73 % |     60.52 % |     69.50 % |     76.13 % |           4.33 px |
| `erop`     |   88.15 % |     75.19 % |     80.27 % |     84.07 % |           2.68 px |

(요약 §6)

own tip @N은 박스 매칭률을 넘을 수 없다. 이를 "박스가 매칭될 확률 × 매칭된 도구의 팁이 N px 안일 확률"로 나누면 다음과 같다.

| 데이터셋   | 박스 미매칭 (GT 도구 대비) | 매칭 도구 중 팁 ≤ 10 px | ≤ 20 px | ≤ 50 px |
| ---------- | -------------------------: | ----------------------: | ------: | ------: |
| `cholec80` |                    19.27 % |                  75.0 % |  86.1 % |  94.3 % |
| `erop`     |                    11.85 % |                  85.3 % |  91.1 % |  95.4 % |

`cholec80`의 own tip @10 손실 39.5 %p 가운데 19.3 %p는 박스를 얻지 못한 도구, 20.2 %p는 박스는 얻었지만 팁이 10 px 밖인 도구에서 온다. `erop`은 11.8 %p와 13.0 %p다. 50 px 기준에서는 매칭된 도구의 94〜95 %가 팁을 맞히므로, **거친 기준에서의 병목은 박스 매칭**이고 10 px 같은 정밀 기준에서는 박스 매칭과 팁 정밀도가 비슷한 크기로 기여한다.

박스 미매칭에는 도구를 아예 놓친 경우와, 탐지는 했지만 박스 IoU가 0.5에 못 미친 경우가 섞여 있다. 화면 가장자리에서 잘린 도구나 서로 겹친 도구는 박스 경계가 모호해 IoU 0.5를 넘기 어렵다. 산출물에는 쌍 매칭의 IoU 분포가 없어 두 경우를 나눌 수 없다(요약 §12).

### 6.2 뒤바뀜의 상한: Hit − own tip

| 데이터셋   | Hit@10 − own @10 | Hit@20 − own @20 | Hit@50 − own @50 |
| ---------- | ---------------: | ---------------: | ---------------: |
| `cholec80` |          1.71 %p |          2.43 %p |          4.47 %p |
| `erop`     |          1.18 %p |          1.60 %p |          2.66 %p |

(요약 §6의 차이 부호를 뒤집은 값)

두 지표는 같은 `conf ≥ 0.25` 예측에서 GT 도구마다 계산된다. 어떤 GT 도구가 own tip @N에서 성공했다면, 그 도구에 매칭된 예측 팁이 N px 안에 있으므로 가장 가까운 예측 팁도 N px 안에 있어 Hit@N에서도 성공한다. 따라서 own tip 성공은 Hit 성공의 부분집합이고, **Hit − own tip은 "근처에 예측 팁은 있지만 그것이 자기 도구의 박스에 붙어 있지 않은" GT 도구의 비율**이다. 여기에는 (a) 박스는 매칭됐지만 그 예측의 팁이 멀고 다른 예측의 팁이 가까운 경우(뒤바뀜)와, (b) 팁은 맞혔지만 박스 IoU가 0.5 미만이라 매칭되지 않은 경우가 함께 들어 있다.

이 값이 10 px 기준 1.71 %p / 1.18 %p이므로, 정밀 기준에서 뒤바뀜은 GT 도구의 2 % 미만이다(Q1). 상한 기준을 넓힐수록 값이 커지는 것은 (b)와, 멀리 떨어진 다른 도구의 팁이 우연히 N px 안에 들어오는 경우가 늘기 때문으로 보인다. 이 모델은 같은 앵커에서 박스와 팁을 함께 내므로 출력 단계에서 짝이 바뀔 수는 없다. 남는 뒤바뀜은 한 도구의 박스를 맡은 앵커가 이웃 도구의 팁을 회귀한 경우다.

이 분석은 뒤바뀜의 **상한**만 준다. (a)와 (b)를 나누려면 `eval-model`이 쌍 매칭 결과(매칭 IoU, 매칭 예측의 팁 거리, 최근접 예측 팁의 소속)를 도구 단위로 기록해야 한다.

## 7. 실패 양상

### 7.1 프레임 단위 실패

`conf ≥ 0.25` 탐지가 하나도 없는 프레임은 GT 팁이 있는 프레임의 3.51 % (`cholec80`) / 3.22 % (`erop`)다(요약 §8). 도구 수별 탐지 실패율은 도구 1개 프레임이 6.25 % / 5.81 %로, 2〜3개 프레임(0.96〜1.41 %)보다 4배 이상 높다. 탐지 실패는 프레임에 탐지가 하나도 없을 때만 세므로, 도구가 여럿이면 그중 하나만 잡아도 실패가 아니다. 도구 1개 프레임의 높은 실패율에는 이 정의의 차이가 들어 있고, 도구가 하나뿐인 프레임에 화면 가장자리로 일부만 보이는 도구가 많을 가능성도 있다. 후자는 산출물만으로 확인할 수 없다.

### 7.2 도구 수별 탐지 성공률 (Hungarian recall)

| 데이터셋                   |    도구 1개 |    도구 2개 |    도구 3개 | 도구 4개 이상 | 1〜3개 전체 |
| -------------------------- | ----------: | ----------: | ----------: | ------------: | ----------: |
| `cholec80` (10 / 50 px, %) | 63.7 / 83.6 | 66.6 / 83.0 | 56.0 / 71.1 |   42.4 / 55.3 |    — / 80.6 |
| `erop` (10 / 50 px, %)     | 76.0 / 87.0 | 80.0 / 89.4 | 72.5 / 81.5 |   61.2 / 69.2 |    — / 87.0 |

(요약 §8)

도구 1〜2개에서는 성공률이 비슷하고, 3개에서 떨어지기 시작한다(50 px 기준 −11.9 %p / −7.9 %p, 2개 대비). 이 하락은 개별 팁 위치를 못 짚어서라기보다 도구 수만큼 탐지를 내지 못해서다. §5.2의 꼬리 분석과 같은 방향이다. 도구 4개 이상 구간은 더 낮지만, §2.3에서 말했듯 이 구간 라벨의 상당수가 가짜 인스턴스일 수 있어 모델 성능으로 해석하지 않는다. 도구 1〜3개만 보면 50 px 성공률은 80.6 % / 87.0 %로, 전체 Hungarian recall@50(79.03 % / 85.97 %)보다 1.6 %p / 1.0 %p 높다.

쌍 지표는 도구 수별로 나눌 수 없다. `per_tip.csv`에 쌍 매칭 결과가 없기 때문이다(요약 §12). 이 모델의 목적이 도구가 겹친 프레임의 짝짓기이므로, 도구 수별 own tip은 다음 평가에서 가장 먼저 보강할 값이다.

## 8. 신뢰도

매칭된 팁의 탐지 점수 중앙값은 0.899 (`cholec80`) / 0.935 (`erop`)이고, 10 px 안에 들어온 팁만 보면 0.911 / 0.939다(요약 §9). p10은 0.535 → 0.652 / 0.714 → 0.787로 올라가, 점수가 낮은 탐지일수록 팁이 부정확한 경향이 약하게 있다. 다만 점수는 `tool` 클래스 점수이고 키포인트 오차는 점수 학습 목표에 들어가지 않는다. 점수가 높은 탐지라도 팁 정확도를 보증하지 않으므로, 팁 신뢰도가 필요한 응용에는 별도 신호가 필요하다. 평가가 `conf = 0.25`로 잘려 있어 그보다 낮은 점수 분포는 볼 수 없다.

## 9. 세션별 편차

`cholec80` 40개 test 영상의 Hit@10 px은 44.3 % (`video50`)〜77.9 % (`video62`)로 33.6 %p 벌어진다(요약 §10). `video50`은 중앙값 오차도 12.31 px로 다른 영상(3.70〜8.20 px)과 동떨어진다. 그 밖의 39개 영상은 52.3〜77.9 %에 분포한다. 영상 단위 분할이므로 이 편차는 미지의 수술 영상에 대한 성능 폭으로 읽을 수 있고, 평균 하나로 `cholec80` 성능을 대표하기에는 폭이 크다.

`erop` 5개 세션은 70.0〜78.1 %로 8.1 %p 안이다. 다만 세션 하나(`doctor_250702_101536`)가 GT 팁의 49.7 %를 차지하고, 프레임 단위 분할이라 세션 간 편차가 실제보다 작게 보일 수 있다.

## 10. 속도

프레임당 5.21 ms (`cholec80`, cuda:1) / 5.20 ms (`erop`, cuda:2), 약 192 FPS다(요약 §11). letterbox, forward, 디코딩, NMS를 포함한 단일 프레임 처리 시간이다. 두 측정이 다른 GPU에서 나왔지만 값이 같아, 이 장비의 GPU 간 차이는 무시할 만하다. 짝짓기 후처리가 필요 없으므로 이 값이 박스·팁 쌍을 얻는 전체 비용이다.

## 11. 한계

- **실행이 데이터셋당 한 번이다.** 시드를 바꾼 반복 실행이 없어 수치의 분산을 모른다. 1〜2 %p 수준의 차이(§6.2의 Hit − own tip 포함)는 이 분산 안에 있을 수 있다.
- **`cholec80`은 수렴하지 않았다(§3.2).** 보고한 `cholec80` 수치는 이 설정의 상한이 아니다.
- **σ = 0.05는 조정하지 않은 값이다.** §3.2의 지연 학습 가설도 σ 실험 없이는 검증되지 않는다.
- **뒤바뀜은 상한만 안다(§6.2).** 박스 미매칭의 내역과 도구 수별 쌍 지표도 산출물에 없다.
- **도구 4개 이상 프레임이 평가에 포함돼 있다(§2.3).** 전체 지표는 이 구간의 라벨 품질 영향을 받는다.
- **`erop`은 프레임 단위 분할이다.** `erop` 수치는 시간적 누수를 포함한다.
- **운용 임계값이 하나다.** `conf = 0.25` 외의 지점은 평가하지 않았다.

## 12. 결론과 다음 단계

Pose 헤드로 박스와 팁을 같은 앵커에서 내는 구조는 의도한 대로 동작했다. 위치가 맞은 팁이 자기 도구에 붙지 않은 경우는 10 px 기준 GT 도구의 2 % 미만이고(Q1), 쌍 단위 성능은 뒤바뀜이 아니라 박스 매칭(미매칭 19.3 % / 11.8 %)과 팁 정밀도(매칭 도구 중 10 px 밖 25.0 % / 14.7 %)에 묶여 있다(Q2). 팁 오차는 5 px 안의 다수와 도구 미탐지에서 오는 긴 꼬리로 갈리며, 도구가 3개 이상인 프레임에서 성공률이 떨어진다(Q3).

다음 단계는 영향이 큰 순서로 다음과 같다.

1. **`eval-model`에 도구 단위 쌍 기록을 추가한다.** 매칭 IoU, 매칭 예측의 팁 거리, 최근접 예측 팁의 소속을 남기면 §6.2의 상한을 실제 뒤바뀜 수로 바꾸고, 도구 수별 own tip을 계산할 수 있다.
2. **`cholec80`을 더 길게 학습하거나 σ를 바꿔 학습한다.** 키포인트 지연 학습의 원인을 가리고 수렴한 수치를 얻는다.
3. **도구 4개 이상 프레임을 제외한 평가 옵션을 둔다.** 루트 프로젝트와 같은 평가 대상에서 수치를 얻는다.
4. **interactive-trainer를 이 모델로 바꾼다.** 후처리 짝짓기(`pair_detections`)가 필요 없어진다.
