# CLAD-Net 실험결과 분석 보고서

> 대상: [baseline/cladnet](../README.md) — Zhao et al. (2023) CLAD-Net을 논문 본문과 Fig. 1–3만 보고
> 순수 PyTorch로 재구현한 것. 저자 공개 코드·가중치는 없다.
>
> 이 문서의 모든 수치는 [summary-results.md](summary-results.md)에 있고, 그 문서는
> `scripts/generate-summary.py`가 `data/model/`·`data/results/`에서 다시 계산한다.

## 요약

- **도구 박스 탐지는 잘 된다.** test 세트에서 `tool` AP@0.5는 cholec80 0.817, erop 0.878이다.
- **팁 탐지가 이전 회차보다 크게 개선됐다.** 탐지 실패율이 39.3 % → 9.6 %(cholec80),
  28.9 % → 6.8 %(erop)로 떨어졌다. 팁 박스를 10 px에서 32 px로 키우고 150 에포크로 늘린 결과이며,
  **부록 A에서 실험 없이 예측한 방향과 크기가 그대로 맞았다** (§5).
- **tooltip-detector와 대등한 수준에 도달했다.** cholec80 Hit@10 px 56.7 %(루트 최고 모델 59.6 %),
  erop 68.5 %(69.5 %)로 근소하게 뒤지지만, 오차 중앙값은 4.93 px·3.23 px로 더 작다.
- **동일 조건에서 YOLOv8s 클론에는 전 지표 뒤진다** (§6). 파라미터가 2/3인데도 더 느리다.
- **150 에포크에서도 수렴하지 않았다.** 최고점이 cholec80 145, erop 147 에포크로 사실상 마지막이다.

## 1. 실험 설정

| 항목             | 값                                                                            |
| ---------------- | ----------------------------------------------------------------------------- |
| 아키텍처         | CSPDarknet53 + cross-layer aggregation attention neck + 앵커 기반 분리형 헤드 |
| 파라미터         | 7,488,483 (논문 보고치 7.5 M)                                                 |
| 클래스           | `tool`(어노테이션 bbox), `tip`(팁 좌표 중심 **32 × 32 px** 박스)              |
| 입력             | 640 × 640 letterbox (원본 736 × 480)                                          |
| 에포크           | **150** (논문과 동일)                                                         |
| 배치 / lr        | 16 / 0.01 (SGD, momentum 0.937, nesterov)                                     |
| 손실             | `0.05·CIoU + 1.0·BCE(obj) + 0.5·BCE(cls)` — 논문 식 (3)                       |
| 증강             | mosaic + 좌우 반전 + HSV 지터                                                 |
| 논문 밖 추가     | warmup 3 에포크, cosine 감쇠, 가중치 EMA                                      |
| `--frame-stride` | **5** (학습 프레임 5장 중 1장)                                                |
| RM 결합          | `sum` (논문 Fig. 3 그대로)                                                    |

### 데이터

| 데이터셋   | train (stride 5 적용) |                          val |   test | test GT 팁 |         test 세션 |
| ---------- | --------------------: | ---------------------------: | -----: | ---------: | ----------------: |
| `cholec80` |       71,032 → 14,207 | 15,312 (에포크당 1,500 표본) | 98,234 |    161,969 | 40편 (video41–80) |
| `erop`     |      108,424 → 21,685 | 36,140 (에포크당 1,500 표본) | 36,142 |     50,718 |             5세션 |

cholec80은 **영상 단위로 분리된** 스플릿(video01–32 train / 33–40 val / 41–80 test)이다.
erop은 영상 내부를 프레임 단위로 섞어 나눈 스플릿이라 인접 프레임이 train과 test에 함께
들어간다(시간적 누수). **erop 수치는 cholec80보다 낙관적으로 읽어야 한다.**

현상이 있었다. 최종 결과에는 영향이 없었지만 원인은 규명하지 않았다.

| `cholec80` |   0.697 |        0.472 |       0.817 |            0.640 |      0.577 |           0.305 |
| `erop`     |   0.788 |        0.575 |       0.878 |            0.749 |      0.698 |           0.400 |

**두 클래스의 난이도 차이가 이전 회차만큼 벌어지지 않는다.** `tip` AP@0.5가 0.58·0.70으로,

> 누적된 값이라 운용 지점의 정밀도가 아니다. 운용 지점은 §4의 Hungarian 표다.

### 읽는 법

**위치 정밀도는 tooltip-detector보다 낫다.** 오차 중앙값이 cholec80 4.93 px, erop 3.23 px로
루트 프로젝트의 어느 모델보다 작다.

**그러나 오탐이 많다.** Hungarian@10 px 정밀도가 0.663·0.714로 `gaussian-tip`(0.772·0.811)에
뒤진다. cholec80에서 FP가 46,628로 `gaussian-tip`(28,526)의 1.6배다. 이전 회차에서 CLAD-Net의
장점으로 꼽았던 "오탐 억제"는 팁 박스를 키우면서 사라졌다 — 신뢰도 천장이 없어진 대신
낮은 임계값을 통과하는 예측이 크게 늘었다.

**꼬리에서도 진다.** Hit@50 px가 cholec80 70.0 %로 세 비교 대상 모두에 못 미친다.

## 5. 팁 박스 32 px 변경의 효과 — 부록 A의 예측 검증

이전 회차(팁 10 px, 30 에포크)를 분석해 **부록 A**에서 실험 없이 32 px을 도출했다.
그 예측이 맞았는지 같은 test 세트에서 확인한다.

| 지표 (cholec80 test)            | 이전 회차 (10 px, 30 ep) | 현재 (32 px, 150 ep) |         변화 |
| ------------------------------- | -----------------------: | -------------------: | -----------: |
| 팁 예측 최대 신뢰도             |                    0.752 |            **0.925** |       +0.173 |
| 10 px 이내 예측의 신뢰도 중앙값 |                    0.370 |            **0.580** |       +0.210 |
| 탐지 실패율                     |                  39.33 % |           **9.56 %** | **−29.8 pp** |
| Hit@10 px                       |                  30.82 % |          **56.65 %** |     +25.8 pp |
| 팁 오차 중앙값                  |                  9.08 px |          **4.93 px** |     −4.15 px |
| tip AP@0.5                      |                    0.156 |            **0.577** |         ×3.7 |
| mAP@0.5                         |                    0.466 |            **0.697** |       +0.231 |

> 위 신뢰도 두 줄은 양쪽 모두 `conf=0.25` 평가에서 읽은 값이라 조건이 같다. 부록 A가 인용하는
> 0.694 / 0.188은 임계값을 0.05로 낮춰 다시 돌린 평가에서 나온 것으로, **잘리지 않은 분포**의
> 값이다. 두 숫자를 섞어 비교하면 안 된다.

**부록 A의 진단이 맞았다.** 병목은 위치 정확도가 아니라 objectness 학습 목표(=IoU)가 만든
신뢰도 천장이었고, 박스를 키우자 천장이 올라갔다(같은 조건에서 최대 0.752 → 0.925). 탐지
실패율이 29.8 pp 줄어든 것이 그 직접적 귀결이다.

**예측치는 보수적이었다.** 부록 A는 비례 계수가 크기와 무관하다고 가정해 32 px에서 신뢰도
중앙값을 0.314로 추정했다. 같은 `conf=0.05` 조건에서 다시 재야 정확한 대조가 되지만,
`conf=0.25`로 잘린 분포에서도 중앙값이 0.580으로 추정치를 웃돈다. 당시 "박스가 커질수록
objectness 목표값의 분산이 줄어 회귀가 쉬워지므로 계수가 올라갈 여지가 있다"고 단서를
달았던 방향과 일치한다.

단, 에포크도 30 → 150으로 함께 늘었으므로 **위 변화를 전부 팁 크기 효과로 볼 수는 없다.**
두 요인을 분리하려면 32 px × 30 에포크 실행이 따로 필요하다.

## 6. YOLOv8s 클론과의 비교 — 조건이 같다

두 베이스라인이 **같은 팁 크기, 같은 프레임 샘플링, 같은 에포크, 같은 입력 크기**로 학습됐다.
아키텍처 비교가 성립한다.

| 조건                             | CLAD-Net                           | YOLOv8s 클론           |
| -------------------------------- | ---------------------------------- | ---------------------- |
| 팁 박스 / stride / 에포크 / 입력 | 32 px / 5 / 150 / 640²             | 32 px / 5 / 150 / 640² |
| 파라미터                         | **7.49 M**                         | 11.14 M                |
| 아키텍처                         | 앵커 기반 + objectness + CAM·RM 넥 | 앵커프리 + DFL + TAL   |

| 지표                   | cholec80 CLAD-Net | cholec80 YOLOv8s | erop CLAD-Net | erop YOLOv8s |
| ---------------------- | ----------------: | ---------------: | ------------: | -----------: |
| mAP@0.5                |             0.697 |        **0.751** |         0.788 |    **0.858** |
| tool AP@0.5            |             0.817 |        **0.835** |         0.878 |    **0.895** |
| tip AP@0.5             |             0.577 |        **0.666** |         0.698 |    **0.821** |
| 탐지 실패율            |            9.56 % |       **8.82 %** |        6.83 % |   **4.79 %** |
| Hit@10 px              |           56.65 % |      **59.87 %** |       68.46 % |  **75.91 %** |
| 팁 오차 중앙값         |           4.93 px |      **3.60 px** |       3.23 px |  **2.04 px** |
| Hungarian@10 px 정밀도 |             0.663 |        **0.759** |         0.714 |    **0.829** |
| 프레임당               |           10.8 ms |       **6.5 ms** |       10.8 ms |   **6.5 ms** |

**모든 지표에서 뒤진다.** 격차가 가장 큰 곳은 팁 클래스(AP@0.5 −0.09, −0.12)와 오탐
(cholec80 FP 46,628 대 30,699)이다. 작은 물체에서 앵커프리 + DFL + 동적 할당의 이점이
두드러진다는 해석이 자연스럽다.

**논문의 주장은 이 데이터·이 과제에서 재현되지 않았다.** CLAD-Net 논문은 더 적은 파라미터로
더 빠르고 정확하다고 보고하지만, 여기서는 파라미터가 2/3인데도 1.7배 느리고 전 지표에서 낮다.
단 논문이 비교한 것은 YOLOv5·YOLOX·YOLOv6이지 YOLOv8이 아니며, 데이터도 다르다.

## 7. 속도

세 모델을 **같은 GPU(RTX A6000, cuda:3), 같은 측정 범위**로 쟀다.

| 모델                     | 파라미터 |   프레임당 |     FPS | 측정 범위                              |
| ------------------------ | -------: | ---------: | ------: | -------------------------------------- |
| YOLOv8s 클론             |  11.14 M | **6.5 ms** | **153** | letterbox + forward + DFL 디코딩 + NMS |
| **CLAD-Net**             |   7.49 M |    10.8 ms |      93 | letterbox + forward + 디코딩 + NMS     |
| tooltip-detector `monai` |  11.45 M |    11.9 ms |      84 | 전처리 + forward + sigmoid + 피크 추출 |

**파라미터가 가장 적은데 중간이다.** 앵커 3개씩 25,200개 후보를 NMS에 넘기는 비용(YOLOv8s는
8,400개)과, CAM이 레벨마다 적응 풀링·업샘플을 4회씩 수행하는 비용(P3에서 80 × 80 × 336 텐서
대상) 때문으로 보인다. 파라미터 수로 드러나지 않는 연산이다.

논문이 보고한 68.5 FPS(GTX 3070 Ti)와는 GPU가 달라 직접 비교할 수 없다.

> 이전 보고서가 인용한 tooltip-detector 19.6 ms는 다른 학습이 GPU를 함께 쓰던 중에 측정된
> 오염된 값이었다. 유휴 GPU에서 4회 반복 측정한 결과는 11.78–12.04 ms로 안정적이다.

## 부록 A — 팁 박스 크기를 32 px로 정한 근거

아래는 **팁 10 px로 학습한 이전 회차**를 분석해 32 px을 도출한 과정이다.
그 예측이 실제로 어떻게 맞았는지는 본문 §5에 있다.
당시 결과는 하나를 가리켰다 — 팁 위치는 정확한데 **신뢰도가 낮아서** 임계값에 걸린다.
왜 낮은지는 손실 정의에서 바로 나오고, 그로부터 적정 크기를 추가 학습 없이 계산할 수 있다.

### 왜 신뢰도가 낮은가 — objectness 목표값이 IoU다

`common/loss.py`는 YOLOv5 관례대로 **objectness의 학습 목표를 예측 박스와 GT 박스의 CIoU**로 둔다.

```python
target_obj[b, a, gj, gi] = iou.detach().clamp(0)
```

추론 시 신뢰도는 `σ(obj) × σ(cls)`이므로, **팁의 신뢰도는 모델이 도달할 수 있는 IoU에 묶인다.**
그런데 한 변 s인 정사각형 두 개가 축 방향으로 d만큼 어긋났을 때

```text
IoU = (s − d) / (s + d)
```

이고, 10 × 10 px 팁 박스는 640 × 640 letterbox에서 **8.7 px**에 불과하다. 중심이 2 px만 틀려도
IoU가 0.63으로, 3 px이면 0.49로 떨어진다. 즉 **거의 완벽하게 맞혀도 objectness 목표가 0.5 언저리다.**

### 데이터가 이 메커니즘과 일치하는가

`conf=0.05`로 평가한 결과의 `per_tip.csv`에서 팁 예측의 중심 오차와 신뢰도를 함께 보면,
신뢰도가 IoU 상한을 그대로 따라 내려간다.

| 중심 오차 (640 공간) | 예측 수 | 측정 신뢰도(중앙값) | IoU 상한 |   비 |
| -------------------- | ------: | ------------------: | -------: | ---: |
| 0–1 px               |   1,453 |               0.251 |    0.857 | 0.29 |
| 1–2 px               |   2,944 |               0.238 |    0.705 | 0.34 |
| 2–3 px               |   2,318 |               0.186 |    0.567 | 0.33 |
| 3–4 px               |   1,256 |               0.171 |    0.437 | 0.39 |
| 4–6 px               |   1,163 |               0.128 |    0.294 | 0.43 |

`신뢰도 ≈ 0.367 × IoU` 로 비례한다. 그 결과가 다음 수치다.

- **10 px 이내로 정확히 맞힌 예측조차 신뢰도 중앙값이 0.188이다.**
- 그중 `conf ≥ 0.25`는 39.3 %, `≥ 0.40`은 16.9 %, `≥ 0.50`은 5.7 %뿐이다.
- 전체 test에서 **팁 예측이 도달한 최대 신뢰도가 0.694**다. 0.7을 넘긴 적이 한 번도 없다.

탐지 실패율 39 %는 모델이 팁을 못 찾아서가 아니라, 찾고도 임계값을 넘길 만한 신뢰도를
구조적으로 낼 수 없어서 생긴 것이다.

### 크기별 투영

측정된 중심 오차 분포(10 px 이내로 맞힌 9,745건, 중앙값 2.17 px @640)를 **그대로 두고**
박스 한 변만 바꾸면 IoU가, 따라서 신뢰도가 어떻게 되는지 계산할 수 있다.

| 팁 박스 (원본 px) | 640 공간 | IoU 중앙값 | 예상 신뢰도 중앙값 | `conf ≥ 0.25` 도달 비율 | 직전 대비 |
| ----------------: | -------: | ---------: | -----------------: | ----------------------: | --------: |
|         10 (현재) |      8.7 |      0.601 |              0.221 |                  34.6 % |         — |
|                16 |     13.9 |      0.731 |              0.268 |                  62.4 % |  +27.8 pp |
|                24 |     20.9 |      0.812 |              0.298 |                  81.5 % |  +19.1 pp |
|            **32** |     27.8 |      0.856 |              0.314 |              **90.6 %** |   +9.1 pp |
|                40 |     34.8 |      0.883 |              0.324 |                  95.5 % |   +4.9 pp |
|                48 |     41.7 |      0.901 |              0.331 |                  98.5 % |   +3.0 pp |
|                64 |     55.7 |      0.925 |              0.340 |                 100.0 % |   +1.5 pp |

**수익 체감이 24–32 px에서 꺾인다.** 32 px을 넘어서면 한 단계 키워도 몇 pp밖에 얻지 못한다.

> 이 투영은 비례 계수 0.367이 크기와 무관하다고 가정한 **보수적** 추정이다. 실제로는 박스가
> 커질수록 objectness 목표값의 분산이 줄어 회귀가 쉬워지므로 계수가 올라갈 여지가 있다.
> 반대로 중심 오차 분포가 그대로라는 가정도 완벽하지 않다 (아래 "정밀도와의 맞교환" 참고).

### 위쪽 한계 세 가지

크기를 무한정 키울 수 없는 이유가 셋 있고, 셋 다 32 px 부근에서 여유가 사라지기 시작한다.

**(1) 앵커 설계.** 앵커는 비율 4배 이내로 매칭된다. 팁 박스가 커지면 매칭되는 앵커가 달라진다.

|    팁 박스 | 매칭되는 앵커                             |
| ---------: | ----------------------------------------- |
|   10–32 px | P3의 (9,9), (22,20), (52,41) — **P3에만** |
|      40 px | 여기에 P4의 (129,61)이 추가된다           |
| 48 px 이상 | (9,9)가 탈락하고 P4 앵커 두 개가 매칭된다 |

`(9,9)` 앵커는 애초에 팁 전용으로 넣은 것이다. 48 px을 넘으면 그 앵커가 무용지물이 되고,
팁이 stride 16 격자에서도 예측되기 시작해 설계 의도가 흐려진다. **32 px까지는 팁이 P3에만
머무른다.**

**(2) NMS 자기 억제.** 같은 크기 정사각형 두 개는 중심 간격이 `0.379 × s`보다 가까우면
IoU 0.45를 넘어 서로를 지운다. 실제 프레임에서 두 팁이 얼마나 가까이 붙는지와 대조하면:

|   팁 박스 | 억제 반경 | 이보다 가까운 팁 쌍의 비율 |
| --------: | --------: | -------------------------: |
|     10 px |    3.8 px |                     0.07 % |
|     24 px |    9.1 px |                     0.56 % |
| **32 px** |   12.1 px |                 **1.11 %** |
|     48 px |   18.2 px |                     2.39 % |
|     64 px |   24.3 px |                     3.93 % |

최대 실패 모드가 **다중 도구 프레임의 과소 탐지**라는 점(본문 §8)을 생각하면, 이 항목은
그냥 넘길 수 없다. 32 px의 1.1 %는 감수할 만하지만 64 px의 3.9 %는 이미 존재하는 약점을 덧낸다.

**(3) 도구 박스와의 구분.** 팁 박스가 도구 박스만 해지면 두 클래스가 시각적으로 구분되지 않는다.
도구 박스 짧은 변의 중앙값은 100 px, p25는 56 px이다.

| 팁 박스 | 도구 박스보다 큰 경우 |
| ------: | --------------------: |
|   10 px |                 3.8 % |
|   32 px |                13.3 % |
|   48 px |                20.5 % |
|   64 px |                29.5 % |

64 px이면 도구 박스 셋 중 하나보다 팁 박스가 커진다. 32 px의 13 %는 대개 도구가 화면 가장자리에
살짝 걸린 경우로, 허용 범위다.

### 정밀도와의 맞교환

박스를 키우면 잃는 것도 있다. CIoU의 중심 오차에 대한 기울기는 `dIoU/dd = −2s/(s+d)²`이므로
`d = 0` 부근에서 **`2/s`에 비례한다.** 즉 32 px 박스는 10 px 박스보다 위치를 정확히 맞추라는
압력이 3.2배 약하다. 중심 좌표의 정밀도가 다소 무뎌질 수 있다.

그럼에도 이 교환은 유리하다고 본다.

- 손실 가중치가 `box 0.05` 대 `obj 1.0`이라, 학습을 지배하는 항은 어차피 objectness다.
- 현재 모델은 **정밀도에 여유가 크고 재현율이 부족한** 상태다 (맞힌 팁의 42 %가 5 px 이내인데
  39 %는 아예 못 찾는다). 정밀도를 조금 내주고 재현율을 크게 얻는 방향이 맞다.
- 32 px에서도 IoU 0.5를 넘기려면 중심이 12.1 px 이내여야 한다. 우리가 관심 있는
  Hit@20 px 기준보다 여전히 엄격하다.

### 결론

**32 × 32 px을 권한다.** 24–40 px이 방어 가능한 범위이고, 그 안에서 32가 다음 이유로 낫다.

1. 정확히 맞힌 예측의 **90.6 %가 기본 임계값 0.25를 넘긴다** (현재 34.6 %). 수익 체감이 시작되는 지점이다.
2. 팁이 **P3 한 레벨에만** 머물러 `(9,9)` 앵커를 포함한 현재 앵커 설계가 그대로 유효하다.
3. NMS 자기 억제 위험 1.1 %, 도구 박스 역전 13.3 %로 두 부작용 모두 아직 작다.
4. [yolov8sclone](../../yolov8sclone/README.md)이 같은 32 px을 쓰므로 **두 베이스라인을 팁 크기라는
   교란 변수 없이 비교**할 수 있다.

**적용됐고, 이 보고서의 본문이 그 결과다.** `common/dataset.py`의 기본값을 `DEFAULT_TIP_BOX_SIZE = 32.0`으로 바꾸고
`--tip-box-size` 인수로 노출했다. 값은 체크포인트에 기록되고, 평가 시 그 값으로 라벨을 다시
만들기 때문에 32 px 모델을 10 px 라벨로 채점하는 사고가 나지 않는다.
이전 회차의 산출물은 `data/model-16x16`·`data/results-16x16`에 남아 있고,
`./baseline/cladnet/run generate-summary --suffix "-16x16"`로 그 회차의 수치 표를 다시 만들 수 있다.

> 크기 변경 없이 지금 당장 얻을 수 있는 개선은 본문 §10의 `conf` 조정이다. 두 방법은 상충하지 않는다 —
> 박스를 키우면 신뢰도 분포 자체가 올라가므로, 기본 임계값 0.25를 유지하면서도 이전 회차에서
> `conf=0.05`로 얻은 것과 비슷한 재현율에 도달하되 오탐은 훨씬 적을 것으로 예상된다.

## 부록 B — 입력 종횡비와 캔버스 모양

"영상을 모델 입력에 맞추면서 종횡비가 바뀐다"는 관찰에서 출발해, 종횡비를 보존하면 성능이
오를지 추가 실험 없이 따져본다.

### 어디에서 실제로 종횡비가 바뀌는가

파이프라인을 단계별로 확인한 결과, **네트워크 입력 단계는 이미 종횡비를 보존한다.**

| 단계                              | 코드                                                      | 종횡비                           |
| --------------------------------- | --------------------------------------------------------- | -------------------------------- |
| 원본 영상 → 데이터셋 PNG          | 데이터셋 구축 (이 저장소 밖)                              | **가로 0.862배로 눌림**          |
| 데이터셋 PNG → 학습 입력 (mosaic) | `dataset._load_scaled` — `scale = image_size / max(h, w)` | 보존                             |
| 데이터셋 PNG → 평가/추론 입력     | `boxes.letterbox` — `scale = min(size/w, size/h)` + 패딩  | 보존                             |
| 데모의 영상 프레임 → 736 × 480    | `sources._fit` — 강제 리사이즈                            | 16:9 입력이면 위와 **같은 눌림** |

실측으로 확인했다.

| 데이터셋   | 원본 영상          | 데이터셋 PNG      | 가로 배율 | 세로 배율 |
| ---------- | ------------------ | ----------------- | --------: | --------: |
| `cholec80` | 854 × 480 (16:9)   | 736 × 480 (1.533) |     0.862 |     1.000 |
| `erop`     | 1920 × 1080 (16:9) | 736 × 480 (1.533) |     0.383 |     0.444 |

즉 **왜곡은 데이터셋을 만들 때 이미 들어갔고**, 그 뒤 단계는 모두 보존한다. 원형인 내시경
시야가 가로로 눌린 타원으로 저장되어 있고, 도구도 실제보다 14 % 좁다.

### 종횡비를 되돌리면 성능이 오르는가 — 아니라고 본다

**세 가지 이유로 기대 이득이 거의 없다.**

1. **학습·평가·데모가 모두 같은 기하를 본다.** CNN은 일관되게 주어진 기하를 그대로 학습한다.
   train과 test의 기하가 어긋날 때만 손해가 나는데, 여기서는 어긋나지 않는다.
2. **앵커가 이미 눌린 데이터에서 뽑혔다.** `model.py`의 앵커는 눌린 736 × 480 좌표계에서
   k-means로 구한 값이라 현재 기하에 맞춰져 있다. 원복하면 앵커를 다시 구해야 한다.
3. **사전학습 가중치를 쓰지 않는다.** 자연 영상 비율을 전제한 ImageNet 사전학습 특징을
   가져오는 것이 아니므로, "실제 비율이어야 특징이 잘 맞는다"는 논거가 성립하지 않는다.

되돌리는 비용은 반대로 크다. 데이터셋 18만 장을 다시 추출해야 하고, 같은 프레임을 쓰던
tooltip-detector와의 **직접 비교(본문 §4)가 깨진다.**

### 정작 손해를 보고 있는 것은 종횡비가 아니라 정사각 캔버스다

736 × 480(AR 1.533)을 640 × 640에 letterbox하면 **캔버스의 34.8 %가 회색 패딩**이다.
물체가 존재할 수 없는 영역에 연산과 손실이 쓰인다.

| 네트워크 입력        | 내용 영역 |       패딩 | 유효 배율 | 연산량 (640² 대비) |
| -------------------- | --------- | ---------: | --------: | -----------------: |
| **640 × 640 (현재)** | 640 × 417 | **34.8 %** |     0.870 |              1.00× |
| 640 × 416            | 638 × 416 |      0.3 % |     0.867 |          **0.65×** |
| 704 × 448            | 687 × 448 |      2.4 % |     0.933 |              0.77× |
| **800 × 512**        | 785 × 512 |      1.9 % | **1.067** |              1.00× |
| 960 × 640            | 960 × 626 |      2.2 % |     1.304 |              1.50× |

같은 연산량으로 **800 × 512**를 쓰면 물체가 23 % 커지고, 같은 해상도로 **640 × 416**을 쓰면
연산이 35 % 준다. 둘 다 종횡비를 바꾸지 않고 얻는 이득이다.

**패딩은 정확도에도 값을 치른다.** `loss.py`의 objectness 항은 모든 셀에 대한 BCE 평균이다.

```python
loss_obj = loss_obj + self.bce(prediction[..., 4], target_obj) * OBJ_BALANCE[level]
```

패딩 셀은 목표값이 0이고 금방 학습되어 손실에 거의 기여하지 않지만, **평균의 분모에는
그대로 들어간다.** 셀 수가 `1/(1−0.348) = 1.53배`로 불어나므로 실제 물체가 있는 셀 하나가
받는 기울기는 **패딩이 없을 때의 0.65배**로 줄어든다. 손실 가중치를 `obj 1.0`으로 정해 놓고
실제로는 0.65로 학습해 온 셈이다.

이 점이 부록 A와 맞물린다. 거기서 확인한 병목이 **objectness가 자라지 못해 생기는 신뢰도 천장**인데,
패딩은 바로 그 objectness의 학습 신호를 1.5배 희석하고 있다. 패딩을 없애면 팁 박스를 키우는 것과
**같은 방향으로** 작용한다.

다만 지렛대의 크기는 다르다. 중심 오차 중앙값 2.17 px(640 공간)에서 팁 박스의 IoU는

- 10 px 박스 @ 640 × 640 → 8.70 px → IoU 0.601 (이전 회차)
- 32 px 박스 @ 640 × 640 → 27.8 px → IoU 0.856 (현재)
- 32 px 박스 @ 800 × 512 → 34.1 px → IoU 0.880

**팁 박스 크기가 주 지렛대이고 캔버스 모양은 보조**다. 다만 보조 쪽은 연산을 더 쓰지 않으므로
같이 취하지 않을 이유가 없다.

### 별도로 고쳐야 할 것 — 데모의 강제 리사이즈

`common/sources.py`의 `_fit()`은 어떤 해상도가 들어와도 736 × 480으로 강제 리사이즈한다.

```python
if frame_rgb.shape[1] != FRAME_W or frame_rgb.shape[0] != FRAME_H:
    frame_rgb = cv2.resize(frame_rgb, (FRAME_W, FRAME_H), ...)
```

현재 두 데이터셋의 원본이 모두 16:9라 결과적으로 학습 때와 같은 눌림이 되어 문제가 드러나지
않는다. 그러나 데모의 `Open File...`은 임의의 영상을 받으므로, **4:3이나 세로 영상을 열면
학습 때와 다른 왜곡**이 적용된다. 잠재적 결함이며, `_fit()`을 letterbox로 바꾸면 해결된다.

### 정리

| 후보                        | 기대 효과                         | 비용                                        | 판단                         |
| --------------------------- | --------------------------------- | ------------------------------------------- | ---------------------------- |
| 데이터셋 종횡비 원복        | 없음에 가깝다                     | 18만 장 재추출, 앵커 재계산, 비교 기준 상실 | **하지 않는다**              |
| 입력을 800 × 512로          | 물체 23 % 확대, obj 기울기 1.53배 | 재학습, 연산량 동일                         | **권한다** (팁 32 px과 함께) |
| 입력을 640 × 416으로        | 연산 35 % 절감                    | 재학습                                      | 속도가 우선이면              |
| 데모 `_fit()`을 letterbox로 | 비-16:9 입력에서의 정확도         | 코드 몇 줄                                  | **권한다** (독립적으로)      |

측정 없이 세운 추론이므로, 800 × 512는 `--image-size`를 두 값으로 받도록 고친 뒤 짧게
검증하는 편이 안전하다. 현재 `--image-size`는 정사각형 하나만 받는다.

## 재현 명령

```bash
# 학습 (완료됨 — data/model/<dataset>/에 산출물이 있다)
./baseline/cladnet/run train-model --dataset cholec80 --frame-stride 5 --val-frames 1500 --device cuda:0
./baseline/cladnet/run train-model --dataset erop     --frame-stride 5 --val-frames 1500 --device cuda:1

# 평가 (완료됨 — data/results/<dataset>/test/에 산출물이 있다)
./baseline/cladnet/run eval-model --dataset cholec80 --split test
./baseline/cladnet/run eval-model --dataset erop     --split test

# 이 보고서가 인용하는 수치 표 재생성
./baseline/cladnet/run generate-summary
```

이전 실험(팁 10 px, 30 에포크)의 산출물은 `data/model-16x16`·`data/results-16x16`에 남아 있고,
`./baseline/cladnet/run generate-summary --suffix "-16x16"`로 그 회차의 수치 표를 다시 만들 수 있다.

자세한 실행 인수는 [docs/commands.md](commands.md), 구조 설명은 [README](../README.md)와
[구조 다이어그램](images/model-architecture.png)을 참고한다.
